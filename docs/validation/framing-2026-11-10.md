# Reply-framing optimization — 2026-11-10

`LineReader` previously searched each newly received segment through generic
`Data` collection indexing. It now uses a bounded `memchr` over the contiguous
bytes. The returned offset is used by the existing UTF-8 decoder and framing
logic; the pointer never escapes the buffer access. No timeout, cancellation,
frame-size, partial-EOF or input-delivery policy changed.

## Measured acceptance

Baseline is `0302b04`. The isolated benchmark compiles the actual reader with
optimization and reads cached local fixtures, excluding simulator and producer
scheduling. Each case has one warm-up and 30 samples:

| Framing case | Previous p95 | Candidate p95 |
|---|---:|---:|
| 1 KiB frame | 0.0138 ms | 0.0078 ms |
| 128 KiB frame | 0.7006 ms | 0.1376 ms |
| 4 MiB frame | 23.31 ms | 8.47 ms |
| 1,000 coalesced Unicode frames | 1.197 ms | 1.215 ms |

The 4 MiB framing p95 improved **63.7%**, exceeding the 20% gate. Small coalesced
messages show no meaningful latency improvement; this is not a universal speedup.

The complete CLI comparison alternates baseline/candidate processes and reverses
their order every sample against the same stub daemon. Thirty samples per path:

| Complete CLI request | Previous p95 | Candidate p95 |
|---|---:|---:|
| Small reply | 21.54 ms | 20.32 ms |
| 128 KiB reply | 26.17 ms | 22.50 ms |
| 4 MiB reply | 75.41 ms | 57.92 ms |
| 20-command batch, stub reply | 16.22 ms | 17.42 ms |

Complete 4 MiB requests improved **23.2%** at p95. Related p95 changes remain
within the regression budget. Candidate 128 KiB requests included one **292.69 ms
maximum** versus the baseline's 31.23 ms maximum; it is retained, not discarded
or assigned an unproven cause. Median/p95 improved, but worst-case latency is not
guaranteed. Full samples, maxima and catalog measurements are in
`framing-2026-11-10.json`. This comparison does not include CoreSimulator or real
UI transitions; watch settling is unchanged.

## Correctness and installation

All **78 tests**, the release build, and transport/protocol/lifecycle regressions
passed. Six added tests cover 16 KiB delimiter boundaries, compaction, exact frame
limits, fragmented Unicode across partial-read timeouts, cancellation with a
buffered next frame, embedded NUL, invalid UTF-8, partial EOF and 1,000 ordered
Unicode/empty frames. Tests use temporary files/pipes and clean up afterward.

No simulator was booted. Cold iOS initialization and accurate Vision OCR remain
the previously recorded limitations. Installed release SHA-256:
`64de58f92655392f7d0d489141b5cd9bf6eaf67d44df858e86533d3a81431a90`.

## Reproduce

```sh
swift test
swift build -c release
wand_bench_dir=$(mktemp -d)
swiftc -O Sources/WandKit/LineReader.swift examples/line-reader-benchmark.swift -o "$wand_bench_dir/reader"
"$wand_bench_dir/reader" /tmp/wand-framing.json 30
git show 0302b04:Sources/WandKit/LineReader.swift > "$wand_bench_dir/before.swift"
swiftc -O "$wand_bench_dir/before.swift" examples/line-reader-benchmark.swift -o "$wand_bench_dir/before"
"$wand_bench_dir/before" /tmp/wand-framing-before.json 30
python3 examples/performance.py .build/release/wand --compare-to /path/to/baseline/wand --output /tmp/wand-cli-compare.json
rm -rf "$wand_bench_dir"
```

`--compare-to` is restricted to stub/CLI measurements. Comparing two client
binaries against one live daemon would not compare the daemon implementations.
