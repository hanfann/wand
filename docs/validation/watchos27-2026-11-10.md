## Measured reductions

These are local measurements, not universal latency guarantees or exact model token counts.

| Surface | Before | After | Meaning |
|---|---:|---:|---|
| MCP tool catalog, minified JSON | 7103 bytes / 27 tools | 502 bytes / 1 tool | 92.9% less catalog payload |
| Skill file | 5337 bytes | 3147 bytes | 41.0% less instruction text |
| 20 warm read-only `ping` calls | 0.1642s, separate CLI processes | 0.0083s, one batch | About 20× less process/socket overhead; not a UI speedup |
| Fast OCR on Settings, final installed binary | Earlier accurate/default path could exceed 6s | 0.4753s | Fast mode uses a bounded CPU worker; quality differs from accurate mode |
| Filtered OCR on identical pixels | New recognition above | 0.0348s / 0.0322s | Exact PNG-content cache, then query filtering; no time-based stale targeting |

An experiment removing repeated AX walks did not improve inert tap latency (medians 0.808s vs 0.825s) and a navigation batch failed during that pass. That experiment was reverted. The original input settling remains. Final tests verify the Settings root before the navigation batch. Successful HID dispatch remains distinct from a verified app outcome.

## Limits

Fast OCR can misread text (for example, Notifications and Smart Stack in Settings). It is an optional perception path, with screenshots/point coordinates as the fallback. Accurate OCR timed out at its 5s worker deadline on this Mac; the next `info` completed in 0.009s, proving the daemon remained usable. Recognition quality is not guaranteed. No image/cache/helper leftovers are retained from timed-out workers.

Batches keep normal settling, stop on failure, and do not roll back earlier actions. Lost replies do not replay commands. Use assertions or fresh observations where an action's result determines the next step. Unrelated daemons were preserved; restart only the selected task daemon after upgrading its binary.
